# Production frontend used a localhost API fallback

**Date:** 2026-09-16 10:52
**Files:** `frontend-next/src/lib/api.ts`, `frontend-next/.env.example`, `frontend-next/src/features/compare/compare-page.tsx`
**Severity:** high

## Problem

The deployed catalog showed `Каталог недоступен`. The browser requested
`http://127.0.0.1:8000/programs`, which points to the visitor's computer,
while the public VM exposes the backend through same-origin `/api`.

## Root Cause

The frontend API client used `http://127.0.0.1:8000` as its fallback when
`NEXT_PUBLIC_API_BASE_URL` was not present at build time. The VM build did not
inject that development-only variable, so the production browser bundle kept
the localhost endpoint. The deployment packaging also required preserving the
Next standalone directory nesting expected by systemd.

## Solution

Changed the production-safe client fallback and example environment value to
`/api`, preserving explicit absolute URLs for local development. Added
configurable `[FIX:catalog-api]` debug logging without logging user data.
Added the comparison category visualization using the existing backend
`areaBreakdownA`/`areaBreakdownB` contract, with accessible A/B progress bars,
percentages, and responsive layout. The VM was redeployed with the exact
`frontend-runtime/.next/standalone/server.js` layout and a preserved rollback.

## Prevention

- Default browser API configuration should be same-origin in production.
- Production browser smoke tests must assert that catalog requests use `/api`
  and never a visitor-localhost URL.
- Deployment archives must validate the exact systemd entrypoint path before
  swapping the active release.
- Keep an explicit rollback release and verify the public route after restart.
